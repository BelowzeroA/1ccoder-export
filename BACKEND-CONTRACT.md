# Контракт сервера 1CCoder

Какие запросы приложение 1CCoder отправляет своему сервису и чего ждёт в ответ. Документ
составлен по коду клиента (`packages/desktop/src/main/llm/`, `src/main/telemetry/`,
`src/renderer/auth/`); где сказано «клиент делает X», это проверяемо в коде.

Сервис — это ваш бэкенд. Модель выбирает он: клиент не называет модель и отправляет
стандартный запрос OpenAI Chat Completions, а сервер решает, какой моделью его выполнить.

Адреса сервиса задаются при сборке: `ONECCODER_SERVER_URLS` (см. `packages/desktop/.env.example`).
Ниже `<base>` — один из этих адресов, без завершающего `/`.

---

## 0. Общее

| | |
|---|---|
| Формат | JSON в UTF-8, кроме загрузки частей (`application/octet-stream`) и потока модели (SSE) |
| Авторизация | Вход по коду из письма даёт **учётные данные** (`credential`, живут ~7 дней). В обмен на них сервер выдаёт **токен** (`token`, живёт ~24 часа), которым подписаны все запросы к модели и телеметрии: `Authorization: Bearer <token>` |
| Ошибки | Тело ошибки — `{"detail": "<текст>", "code": "<машинный код>"}`; `code` нужен там, где он назван ниже |
| Соединения | Клиент открывает **новое TCP-соединение на каждый запрос** и не рассчитывает на keep-alive (так обходятся сети, обрывающие соединение после ~16–24 КБ) |
| Размер тела | Тело запроса больше `chunk_size` клиент не шлёт одним запросом: он делит его на части (§3) |

Несколько адресов: клиент опрашивает `GET <base>/health` у каждого (если адресов больше одного) и
работает с первым по порядку, который ответил `2xx` за 5 секунд. После двух сбоев подряд он
опрашивает список заново; раз в 10 минут проверяет, не ожил ли более предпочтительный адрес.

## 1. `GET /health`

Любой ответ `2xx` означает «адрес жив». Тело не читается. Без авторизации.

## 2. Вход

Экран входа: пользователь вводит e-mail (и при регистрации необязательный телефон), сервер
отправляет на e-mail **шестизначный код**, пользователь вводит его. Отправка письма — забота
сервера.

### `POST /register`

```json
{ "email": "user@example.com", "phone": "+7 900 000-00-00" }
```

`phone` — строка или `null`. Ответ `200`: `{"token": "<токен шага входа>"}` — непрозрачная
строка, клиент вернёт её в `/confirm`.

### `POST /login`

```json
{ "email": "user@example.com" }
```

Ответ `200`: `{"token": "<токен шага входа>"}`.

### `POST /confirm`

```json
{ "token": "<из /register или /login>", "code": "123456" }
```

Ответ `200`:

```json
{ "email": "user@example.com", "credential": "<учётные данные>", "expires_at": 1792000000 }
```

`expires_at` — **секунды** Unix. Клиент хранит учётные данные до этого момента и сам показывает
экран входа, когда срок вышел; сервер всё равно должен отвергать просроченные.

### Ошибки входа — как их понимает клиент

| Ответ | Что увидит пользователь |
|---|---|
| `403` с `code: "account_blocked"` (на любой из трёх) | «учётная запись заблокирована» + контакт поддержки |
| `409` на `/register` | «уже зарегистрирован, войдите» |
| `404` на `/login` | «такой учётной записи нет» |
| `429` | «слишком много попыток, подождите» |
| `5xx` | «ошибка сервера» |
| `400` на `/confirm` | различается **по тексту `detail`** (без учёта регистра): содержит `expired` — код истёк; `too many incorrect` — исчерпаны попытки; `already-used` или `invalid or already` — шаг входа недействителен; иначе — неверный код |
| `422` и прочее | «неизвестная ошибка» |

## 3. Модель

### `GET /llm/config`

Без авторизации. Клиент читает его один раз, при запуске. Все поля необязательны:

```json
{
  "chunk_size": 12000,
  "model_limits": { "context": 200000, "output": 32000 },
  "heartbeat_seconds": 10,
  "servers": ["https://relay.example.com", "https://api.example.com"]
}
```

| Поле | Что делает клиент |
|---|---|
| `chunk_size` | Байт в одной части загрузки и порог «отправить целиком». По умолчанию 12000 |
| `model_limits` | Окно контекста и предел ответа модели, в токенах. По ним клиент показывает заполненность контекста и решает, когда сжимать историю. `null` — неизвестно |
| `heartbeat_seconds` | Сервер шлёт комментарии SSE в паузах потока (ниже). Тогда клиент считает соединение замёрзшим, если по нему не пришло **ни одного байта** за `max(30 с, 3 × heartbeat_seconds)` |
| `servers` | Новый список адресов в порядке предпочтения; заменяет вшитый при сборке |

### `POST /llm/token`

```json
{ "credential": "<учётные данные из /confirm>" }
```

Ответ `200`:

```json
{ "token": "<токен>", "expires_at": 1792000000, "chunk_size": 12000 }
```

`expires_at` — секунды Unix; клиент обновляет токен за минуту до срока. `chunk_size`
необязателен. Отказ: `403` с `code: "account_blocked"` — заблокирован; прочие отказы — «не вошёл».

Сервер должен **при каждом запросе к модели** проверять, не заблокирована ли учётная запись, а не
только при выдаче токена: блокировка действует со следующего запроса.

### `POST /llm/v1/chat/completions`

Запрос в формате OpenAI Chat Completions, как его формирует `@ai-sdk/openai-compatible`:
`messages`, `tools`, `stream: true` (почти всегда), `stream_options`, `max_tokens` и т. п.
Поле `model` всегда `"default"` — модель выбирает сервер. Изображения приходят частями
`image_url` (data URL).

Заголовки:

| Заголовок | |
|---|---|
| `Authorization: Bearer <token>` | всегда |
| `X-1CCoder-Session: <id>` | идентификатор сеанса, если есть. По нему удобно учитывать расход по сеансам |
| `X-1CCoder-Upload-Id: <id>` | только у собранного из частей запроса; тела тогда нет (ниже) |

**Ответ на `stream: true`** — поток SSE в формате OpenAI: строки `data: {chunk}` и в конце
`data: [DONE]`. Клиент считает ответ полным, если увидел `[DONE]` или непустой
`"finish_reason"`; поток, закрытый без этого, считается оборванным, и ход повторяется.

Требования к потоку:

- **Паузы.** Модель может думать долго. Клиент ждёт первого байта ответа до 600 с, а в потоке —
  до 210 с между событиями `data:`. Чтобы долгое молчание не принимали за обрыв, шлите
  комментарии SSE (строки, начинающиеся с `:`) каждые `heartbeat_seconds` и объявите это в
  `/llm/config`. Комментарии не считаются продвижением ответа, только признаком живого соединения.
- **Ошибка посреди потока.** Если модель отказала после начала ответа, пришлите событие
  `data: {"error": {"message": "...", "type": "..."}}` и затем `data: [DONE]`. Клиент
  считает такой ответ потерянным и повторяет ход (не более 3 потерь подряд за 30 минут — потом
  останавливается и объясняет пользователю).

**Ошибки до начала потока** (обычный HTTP-статус и JSON):

| Статус | Тело | Что делает клиент |
|---|---|---|
| `401` | любое | один раз обновляет токен (`/llm/token`) и повторяет запрос |
| `402` | `{"detail": "...", "code": "credits_exhausted", "period_end": <секунды>}` | говорит «кредиты закончились до <дата>», ход не повторяет. `402` без этого `code` — обычная ошибка |
| `403` | `{"detail": "...", "code": "account_blocked"}` | говорит «доступ приостановлен», ход не повторяет |
| `429`, `5xx` | любое | считает ответ потерянным, ход повторяется |
| прочие `4xx` | любое | показывает текст ошибки, ход не повторяет |

### `POST /llm/upload/{upload_id}/{index}` — загрузка по частям

Тело больше `chunk_size` клиент сначала загружает частями, затем вызывает
`/llm/v1/chat/completions` **без тела** с заголовком `X-1CCoder-Upload-Id`. Сервер собирает
части по порядку индексов и обрабатывает результат как обычное тело запроса.

| | |
|---|---|
| `upload_id` | `[a-z0-9]`, до 40 символов, создаёт клиент |
| `index` | `0 … total-1` |
| Заголовки | `Authorization: Bearer <token>`, `X-Total-Chunks: <total>`, `Content-Type: application/octet-stream` |
| Ответ | любой `2xx` (тело не читается); не-`2xx` прерывает отправку, клиент показывает ошибку |

На сборке: нет такой загрузки — `404`; не хватает части — `400` с номером недостающей. Части
после сборки стоит удалять, незавершённые — по таймауту.

### `GET /llm/balance`

`Authorization: Bearer <token>`. Клиент запрашивает его через 1,5 с после каждого запроса к
модели и показывает остаток.

```json
{ "credits_spent": 6.18, "credits_limit": 10.0, "credits_left": 3.82, "period_end": 1793491200, "status": "active" }
```

`credits_left` и `credits_limit` обязательны (числа), иначе ответ игнорируется. `period_end` —
секунды; `status` — `"active"` или `"blocked"`. Если кредитов у вас нет, отвечайте `404`: клиент
просто не покажет остаток.

## 4. Телеметрия

Клиент собирает в фоне сеансы, профили (без паролей), созданные обработки, сведения о системе и
журналы и отправляет их серверу. **Включено ли и что именно — решает сервер**, ответом
`/telemetry/config`. Значения секретов в отправляемом заменяются на `***`.

**Минимум, если телеметрия вам не нужна:** отвечайте на `GET /telemetry/config` так:

```json
{ "enabled": false }
```

Без этого ответа клиент считает сервер временно недоступным, копит данные в очереди и пытается их
отправить. Все запросы ниже — с `Authorization: Bearer <token>`.

### `GET /telemetry/config`

```json
{
  "enabled": true, "artifacts": true, "logs": true,
  "max_artifact_bytes": 10485760, "max_log_bytes": 5242880,
  "sync_seconds": 120, "chunk_size": 12000
}
```

`sync_seconds` — период отправки; `artifacts` и `logs` включают соответствующие виды.

### `GET /telemetry/has/{sha256}`

Есть ли уже у сервера файл обработки с таким SHA-256 (от этой учётной записи): `{"exists": true}`.
Клиент не отправит его повторно.

### `POST /telemetry/upload/{upload_id}/{index}`

Как `/llm/upload` (§3): части большого объекта перед `/telemetry/commit`.

### `POST /telemetry/commit`

```json
{ "kind": "session", "meta": { ... }, "content_b64": "<base64>" }
```

или вместо `content_b64` — `"upload_id": "<id>"` загруженного по частям. Ответ:
`{"stored": true}` или `{"stored": false, "reason": "..."}` (клиент не повторяет). Ответ `4xx`
кроме `401` и `429` — объект отбрасывается; `401`, `429`, `5xx`, сеть — повтор позже.

| `kind` | `meta` | Содержимое |
|---|---|---|
| `session` | `session_id`, `seq` (порядковый номер пакета в сеансе), `parent_session_id`?, `profile_id`?, `title`?, `app_version`, `schema` (версия opencode) | gzip, JSONL строк `{table, row}` из базы opencode: `session`, `message`, `part`, `todo` |
| `profile` | `profile_id` | JSON профиля без пароля |
| `artifact` | `sha256`, `ext` (`epf`, `erf`, `cfe`, `mxl`), `profile_id`, `path` (относительно рабочего каталога), `mtime` (мс) | файл как есть |
| `env` | `app_version` | JSON: версии, ОС, память, процессоры, локаль, пути к платформам 1С, адрес сервиса |
| `skills` | `app_version` | JSON: имена установленных навыков и хеш их каталога |
| `log` | `date` (`YYYY-MM-DD`), `name` | gzip хвоста журнала, не больше `max_log_bytes` |

## 5. Обновления

Приложение обновляется через electron-updater (провайдер `generic`). Каталог обновлений:
`ONECCODER_UPDATES_URL` при сборке, по умолчанию `<base>/updates/`; бета-канал — `.../beta/`.
Приложение берёт тот адрес сервиса, с которым работает сейчас, поэтому каталог должен быть
доступен **по каждому адресу** из списка, по пути `/updates/`.

Содержимое: `latest.yml`, установщик `1ccoder-setup-<версия>.exe` и его `.blockmap` — их
создаёт `electron-builder` (см. RELEASE.md). Выкладывайте `latest.yml` последним, чтобы клиент не
увидел новую версию, пока установщик ещё загружается.

## 6. Чек-лист минимального сервера

1. `GET /health` → `200`.
2. `POST /register`, `/login`, `/confirm` с письмом-кодом.
3. `GET /llm/config` → хотя бы `{}`; лучше с `model_limits` и `heartbeat_seconds`.
4. `POST /llm/token`.
5. `POST /llm/v1/chat/completions` с потоком SSE, `POST /llm/upload/...`.
6. `GET /telemetry/config` → `{"enabled": false}`.
7. `GET /llm/balance` → данные или `404`.
8. Каталог `/updates/` — если нужны автообновления.
